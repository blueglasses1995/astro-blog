## 2. ミッション（Mission）
本プロジェクトは、以下の2つを両輪として進める。

1. **技術ブログの構築と運用**  
   - 自身の技術的学びを整理・共有し、フリーランスとしての信頼性と専門性を示す名刺代わりとする。

2. **知識基盤（Knowledge Base）の構築**  
   - 日々の実験や調査ログ、AIとの対話内容を蓄積・検索可能なデータベースとして整理し、将来的な再利用と自動生成を可能にする。

---

## 3. 基本原則（Principles）
- **再現性**：すべての開発・構築手順は Git により再現可能であること。  
- **一貫性**：デザイン、命名、ディレクトリ構造は統一する。  
- **可読性**：文章・コードともに他者が理解できる構造を保つ。  
- **軽量性**：アプリはミニマルで高速に動作することを優先する。  
- **多言語対応**：日本語・英語・中国語を基本とし、国際的に読める構成を心がける。  
- **継続的改善**：すべての方針は実運用に合わせて見直し・更新する。

---

## 4. 品質基準（Quality Standards）

### 4.1 表示品質（Readability）
- 行長は 60〜80 文字以内、行間は 1.5 倍を目安とする。  
- 見出し階層は最大 3 段階まで。  
- コードブロックはシンタックスハイライト付きで明確に記述する。  
- ダーク／ライト両テーマでの可読性を確保する。

### 4.2 パフォーマンス（Performance）
| 指標 | 目標値 | 備考 |
|------|---------|------|
| 初回ロード時間 | 2 秒以内 | モバイル環境では 3 秒以内 |
| Lighthouse スコア | 90 以上 | Performance / Accessibility 両方 |
| 画像サイズ | 1 枚あたり 500KB 以下 | WebP または AVIF 形式推奨 |

### 4.3 テスト・品質保証
- 単体テストは主要ロジックの 80%以上をカバー。  
- ビルド後の静的サイトを自動テストでリンク切れ検証。  
- デプロイ前に自動 Lint・フォーマットチェックを実行。

---

## 5. アーキテクチャ方針（Architecture Doctrine）
- **構成分離**：  
  - 知識基盤（バックエンドAPI）と技術ブログ（フロントエンド）は独立構成とする。  
  - 双方は REST API または GraphQL 経由で連携可能な設計とする。  
- **インフラ**：  
  - Docker コンテナで統一。Terraform による IaC 管理を行う。  
  - CI/CD は GitHub Actions による自動ビルド・デプロイ。  
- **監視・運用**：  
  - 可用性指標（SLO）を定義：稼働率 99.9%、平均復旧時間 < 15分。  
  - OpenTelemetry または類似ツールで観測可能性を確保。
